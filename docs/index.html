Model Context Protocol server · reference implementation

Let AI agents triage fintech operations without giving them authority over identity, tenant data, or money movement.

The server takes the caller's identity from a verified JWT, never from tool arguments. It returns only the fields each role may see, and stages every freeze or refund for a second, step-up-authenticated human to approve. Each decision is written to an append-only ledger keyed with HMAC and anchored by signed checkpoints.

Where an agent helps, and what the server still controls

Four workflows the current tools support. Tool names are the MCP tools the server advertises.

KYB alert triage

read
Agent does
Pulls the merchant or account profile, recent transactions and sub-threshold structuring clusters, then drafts a triage note.
Server enforces
Tenant from the JWT; junior analysts receive initials, ****last4 and masked tax IDs; counterparty memos arrive as untrusted_text; limit is capped at 100 rows.

AP and ledger reconciliation

stage
Agent does
Spots duplicate fees or settlement mismatches and stages a refund or freeze with a reason and an idempotency key.
Server enforces
Amounts are Decimal Money; cumulative refunds never exceed the original; the approval is HMAC-bound to its exact arguments; execution needs a different officer with step-up amr.
Tools
request_fee_refundrequest_account_freezeexecute_approved_action

Audit preparation

verify
Agent does
Nothing privileged. Reviewers run the chain verifier and export decision rows by tenant and time window.
Server enforces
Rows hold structured codes, never free text or PII. The verifier reports the first failing event with a code: EVENT_ID_GAP, ENTRY_HMAC_MISMATCH, TRUNCATION_DETECTED, CHECKPOINT_FORGED.

Operational telemetry

observe
Agent does
Nothing. Every tool call, including SDK-level argument rejections, records latency, decision and reason code.
Server enforces
Telemetry rows have no identity, argument or tenant columns. The Workbench shows p50/p95 latency per tool, blocked calls by reason, Four-Eyes turnaround and expiry rate.

What runs today, and what does not

Demo runtime SQLite

The services, MCP tools and Workbench run on SQLite with triggers that enforce the approval state machine and the append-only ledger.

Postgres 17 schema live-tested

001_schema_rls.sql passed 7/7 live tests on Postgres 17.12. The data-access layer has not been ported to it yet.

Payments sandbox only

A fake gateway and a Stripe test-mode adapter that refuses any key without the sk_test_ prefix. Neither is wired into Four-Eyes execution; refunds stay internal ledger rows.

Keys and anchors dev adapters

Keys come from env vars or a 0600 dev file. Checkpoints go to a local JSONL file. Production needs a KMS- or HSM-held key and a WORM store; no S3 Object Lock adapter is written.

Step-up auth simulated

The Workbench mints amr=mfa tokens in development. A real IdP with WebAuthn or OTP is required before production use.

Run the Risk Workbench locally

The Streamlit Workbench is not hosted yet. It runs locally against a seeded SQLite ledger.

The Workbench has four tabs: Agent & Guardrail Simulator, Four-Eyes Approval Queue, Audit Ledger & Tamper Lab, Operational Telemetry.
