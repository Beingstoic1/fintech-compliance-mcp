Scenario 01

Structuring & Smurfing AML Alert Triage

RBAC + PII Redaction + Tenant Isolation

A Junior AML Analyst agent is assigned to triage automated alerts for sub-threshold smurfing patterns (e.g., repeated transactions just below ₹10,000 threshold to evade mandatory reporting).

Unprotected Agent (Direct DB / API)

The agent queries the core banking table directly using a raw client query:

SELECT * FROM accounts WHERE tenant_id = 'b2b_cards'
  • Cross-tenant leakage: Analyst in retail partition reads enterprise partner data.
  • Cleartext PII: Raw PAN (ABCDE1234F) and full account number (123456784821) enter LLM prompt context.
  • Regulatory failure: Violates RBI Master Direction on KYC & SOC 2 data containment.
Guardrailed MCP (Zero-Trust)

The agent invokes detect_structuring_anomalies with its scoped session token:

{
  "decision": "REDACT",
  "account_number": "****4821",
  "tax_id": "XXXXX234F",
  "tenant_enforced": "tenant_neobank_in"
}
  • Session-bound tenant isolation blocks cross-tenant query with TENANT_ISOLATION_VIOLATION.
  • PII regex automatically redacts account numbers to last 4 digits and PAN to masked format.
  • Non-PII numeric values like amount_cents remain uncorrupted for fraud calculations.
Scenario 02

High-Risk Account Freeze (Four-Eyes HITL Control)

Dual-Control + Single-Use TTL Gate

A Senior AML Investigator determines that an account is orchestrating an active smurfing ring and flags it for an immediate freeze to halt outward fund transfers.

Unprotected Agent (Direct Mutation)

The agent immediately calls a mutating endpoint freeze_account("ACC-010"):

POST /api/v1/accounts/ACC-010/freeze
{ "status": "FROZEN", "by": "agent_auto_gpt" }
  • Autonomous false positive: Legitimate merchant receivables ($500k+) frozen without human confirmation.
  • Rogue self-approval: Any compromised actor token can unilaterally halt payment operations.
  • Audit void: No immutable record of who authorized the operational freeze.
Guardrailed MCP (Four-Eyes HITL Gate)

The agent calls request_account_freeze, generating a 15-minute gate:

{
  "decision": "ESCALATE",
  "approval_id": "8d3e5f7a-2b4c-4e6a-...",
  "args_sha256": "4a7b9c1e5f8a2c...",
  "status": "PENDING",
  "expires_in_seconds": 900
}
  • Strict Four-Eyes control: The requesting senior investigator cannot approve their own ticket (DUAL_CONTROL_VIOLATION).
  • A verified Compliance Officer must review the canonical evidence and sign off.
  • Atomic database consume prevents double-execution or replay.
Scenario 03

Fee Refund Guardrails & Replay Protection

Argument-Bound Hash Binding + TOCTOU Lock

A customer support agent detects a disputed ₹500 duplicate transaction fee and requests a balance credit refund.

Unprotected Agent (Parameter Drift & Replay)

The agent sends repeated refund requests or an adversary intercepts the API call:

POST /api/v1/refunds
{ "transaction_id": "TXN-N001", "amount": 50000 }
  • Replay vulnerability: The same API call executed 20 times issues duplicate refunds, draining reserve capital.
  • Argument tampering: Adversary modifies amount from ₹500 to ₹50,000 between sign-off and execution.
  • Error leakage: Failed database calls dump raw Python stack traces into agent context.
Guardrailed MCP (Cryptographic Binding)

Execution strictly verifies args_sha256 = SHA256(tool || canonical_json || requester_sub):

{
  "decision": "EXECUTED",
  "action": "execute_approved_action (refund)",
  "atomic_lock": "CONSUMED",
  "replays_blocked": true
}
  • Any alteration to amount or transaction ID invalidates the cryptographic hash binding.
  • Atomic SQL status transition marks ticket CONSUMED, blocking concurrent double-execution.
  • Safe error sanitization: Bad transactions return ACTION_EXECUTION_FAILED with zero stack leakage.
Scenario 04

Regulatory Audit & Cryptographic Chain Verification

SHA-256 Hash Chaining + Row Deletion Detection

During a periodic SOC 2 Type II or RBI audit, internal regulators must prove that no audit records have been retroactively modified or wiped by an insider or database administrator.

Traditional Database Logs (Vulnerable)

Standard SQLite or relational table stores plain audit rows:

UPDATE audit_log SET decision = 'ALLOW' WHERE event_id = 14;
  • Silent tampering: Rogue admin or SQL injection alters historical entries undetected.
  • Row deletion: Deleting a non-compliant event leaves no cryptographic proof of removal.
  • Audit failure: Cannot satisfy non-repudiation requirements under financial compliance mandates.
Guardrailed MCP (SHA-256 Chained Ledger)

Every audit entry commits to the previous row's cryptographic signature:

entry_hash = SHA256(prev_hash || timestamp || session || role || tool || args_sha256 || decision)
  • Bit-flip sensitivity: Changing a single character in row #14 causes row #15's prev_hash check to fail immediately.
  • Row deletion detection: Removing any row breaks the genesis-to-tip hash continuity.
  • Automated verifier pinpoints the exact corrupted event ID in < 2 milliseconds.
