Without the server, and with it

Identities below are the demo directory's (for example junior_alice in tenant_neobank_in). In every case the identity comes from the bearer JWT, never from tool arguments.

Runbook 01 · junior_analyst

KYB and structuring alert triage

REDACTget_account_profiledetect_structuring_anomalies

An L1 analyst's agent triages sub-threshold structuring alerts: repeated debits just under ₹10,000 across linked accounts within 48 hours.

Direct DB access

  • Rows from every tenant reach the model context.
  • Full names, account numbers and tax IDs enter the prompt and the model vendor's logs.
  • No record of who read what.

Through the server

  • Tenant comes from the JWT. Another tenant's account returns Account not found, the same response as a nonexistent one.
  • Junior masks: initials, ****last4, format-aware tax-ID mask. Fields not on the tool's allowlist are dropped.
  • Amounts stay exact for analysis; limit is capped at 100 rows at the boundary and again in the DAL.

Runbook 02 · senior_investigator → compliance_officer

High-risk account freeze under Four-Eyes

ESCALATErequest_account_freezeexecute_approved_action

An investigator concludes that an account is part of a structuring ring and wants outbound transfers stopped.

Direct API access

  • A false positive freezes a legitimate merchant with no human review.
  • One compromised token is enough to stop payments.
  • No durable record ties the freeze to an approver.

Through the server

  • Nothing changes until a compliance officer in the same tenant, who is not the requester, approves in the human console with step-up amr (mfa, otp, hwk, swk or fido).
  • There is no approve tool over MCP. Agent tokens carry amr=pwd, so an agent cannot sign its own request.
  • Execution requires APPROVED, runs once, and expires 15 minutes after staging.

Runbook 03 · AP and ledger operations

Fee refund with argument binding and idempotency

EXECUTED oncerequest_fee_refund

A support agent finds a duplicated ₹500 fee and stages a refund.

Direct API access

  • Retries and loops issue duplicate refunds.
  • The amount can change between sign-off and execution.
  • Floating-point amounts drift; stack traces leak into the agent's context.

Through the server

  • Amounts are Decimal Money in a single currency. Requests that are zero, negative, boolean, float, or over the remaining refundable balance are refused with a rule code.
  • Changing any bound argument after approval fails verification. Stored rows are immutable (APPROVAL_ROW_IMMUTABLE).
  • The same idempotency_key returns the same approval_id or the stored result. A failed action returns ACTION_EXECUTION_FAILED with no internals and does not consume the approval.

Runbook 04 · audit preparation

Audit-trail verification

ok: trueverify_audit_chain()

Before a control review, the team has to show that no decision row was edited, removed or appended out of order.

Plain log table

  • Edits and deletions leave no trace.
  • An unkeyed hash chain can be recomputed by anyone who can write the table.
  • Free-text log fields collect PII.

Through the server

  • Triggers abort UPDATE, DELETE and INSERT OR REPLACE on audit tables with AUDIT_LOG_APPEND_ONLY.
  • Entries are HMAC-keyed. Signed checkpoints catch tail truncation. Failures name the event and a code such as ENTRY_HMAC_MISMATCH or TRUNCATION_DETECTED.
  • The detail column holds a code and typed references only; anything else is stored as INVALID_DETAIL.

Client setup

Connecting an MCP client

Streamable HTTP authenticates every request with a bearer JWT. stdio has no per-request auth, so the operator binds one verified identity at launch.

JWTs must carry sub, role and tenant_id claims plus exp/iat/nbf/iss/aud, with a lifetime of 1 hour or less. With no key configured, the server generates an ephemeral per-process key, so tokens minted anywhere else will not verify.
